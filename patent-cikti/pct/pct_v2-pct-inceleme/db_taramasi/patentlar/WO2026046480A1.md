## Abstract

The invention relates to a computer-implemented method for testing a function of a technical system (130) in a test case, the method having a first step (S1) of receiving, in a request input part (311), one or more text-based requests which define at least one test case, said requests at least partly comprising natural language; a second step (52) of generating at least one regular expression for each text-based request (350) in a request checking part (312); a third step (53) of generating a test-case database (350) from the regular expressions for each request in a data structuring part (340); a fourth step (S4) of receiving one or more pieces of test-case-specific parameter information in a parameter information part (313); a fifth step (S5) of combining at least one regular expression of the test-case database (350) with at least one piece of test-case-specific parameter information in order to form one or more test-case schemes in a selection part (331); a sixth step (S6) of generating a test-case-specific algorithm from the one or more test-case schemes in a test-generation part (333); and a seventh step (S7) of transmitting the test-case-specific algorithm into a test environment (150); testing the function of the technical system (130) by executing the test-case-specific algorithm, by means of a test-case peripheral device (140) within the test environment (150); returning the test results to the computer system (200); and carrying out an evaluation by comparing at least one test result with a test-case-specific parameter.

Hintergrund Background

Sowohl auf dem Gebiet der Softwareentwicklung als auch in der Anforderungsanalyse und der Testfallautomatisierung im Allgemeinen herrscht das Problem vor, vollständige und nach vordefinierten Regeln aufgestellte Anforderungen zu erhalten und mittels diesen zu entwickelnde Software, Produkte oder technische Systeme automatisiert oder auch autonom zu testen. Innerhalb der Softwareentwicklung entsteht heutzutage die Tendenz von linearen Entwicklungsmethoden, wie dem klassischen „V-Modell“, zu kontinuierlicher Entwicklung überzugehen. Mittels Methoden des maschinellen Lernens oder künstlicher Intelligenz kann die kontinuierliche Softwareentwicklung effizienter gestaltet werden, beispielsweise als Unterstützung bei der Anforderungsanalyse, dem Generieren von Software- und Programmcode, dem autonomen Testen sowie bei der Daten- und Fehleranalyse. Um die genannten Potentiale in eine reale Zeit- und Ressourcenersparnis umzuwandeln sind auf der einen Seite zwei wesentliche Eckpunkte erforderlich. Zum einen sollten Anforderungen nach aufgestellten Regeln vordefinierte Eigenschaften enthalten, sodass aus diesen automatisiert oder autonom Testfälle erzeugt und durchgeführt werden können. Zum anderen sollte eine potentielle Testumgebung der Software, des Produkts oder des technischen Systems in der Art ausgeführt sein, um eingehende Anforderungen automatisiert oder autonom zu testen. Auf der anderen Seite kann der Konflikt entstehen, dass Anforderungen in einer Vielzahl unterschiedlicher Formen aufgestellt werden, beispielsweise in unterschiedlichen Sprachen oder unterschiedlichen Strukturen der gleichen Sprache, sodass diese für die Implementierung innerhalb der Testumgebung zunächst vereinheitlicht werden müssen. Zudem kann es erforderlich sein, die aufgestellten Anforderungen in eine maschinenlesbare Sprache oder auch Programmcode zu konvertieren. Hierbei kann weiterhin das Problem entstehen, dass ein möglicher Benutzer einen potentiellen Testfall und dazugehörige Anforderungen zwar gedanklich vorliegen hat, jedoch nicht über ausreichend Kenntnisse oder Ressourcen verfügt, um diese in ein entsprechendes Format zu konvertieren. Hieraus entsteht das Begehren einer technischen Lösung, welche den Fachmann dazu befähigt, Eingaben aus natürlicher Sprache in Anforderungen umzuwandeln, welche aufgestellten, vordefinierten Regeln folgen und diese automatisiert oder autonom in Testumgebungen zu überführen und Testfälle auszuführen. Stand der Technik In both software development and requirements analysis and test case automation in general, the prevailing problem is obtaining complete requirements formulated according to predefined rules and using these requirements to automatically or autonomously test the software, products, or technical systems to be developed. Within software development, there is currently a trend away from linear development methods, such as the classic "V-model," towards continuous development. Machine learning and artificial intelligence methods can make continuous software development more efficient, for example, by supporting requirements analysis, software and program code generation, autonomous testing, and data and error analysis. To translate these potentials into real time and resource savings, two key elements are necessary. First, requirements should contain predefined properties according to established rules so that test cases can be generated and executed automatically or autonomously. Second, the potential test environment for the software, product, or technical system should be designed to allow for the automated or autonomous testing of incoming requirements. On the other hand, a conflict can arise when requirements are formulated in a variety of different forms, for example, in different languages or with different structures within the same language, meaning they must first be standardized for implementation within the test environment. Furthermore, it may be necessary to convert the formulated requirements into a machine-readable language or even program code. Another problem can occur here: a potential user may have a conceptual understanding of a test case and its associated requirements, but lacks the necessary knowledge or resources to convert them into a suitable format. This leads to the desire for a technical solution that enables experts to transform natural language input into requirements that follow predefined rules and then automatically or autonomously transfer these requirements into test environments and execute test cases. In one embodiment, the generation of at least one regular expression for each text-based requirement is performed by a first machine learning language processing model (LLM), which is created using training data based on regular, text-based requirements that comply with predefined rules, including one or more of the syntax, grammar, atomicity, conciseness, uniqueness, consistent language, schema following, design independence, and purpose independence. Die korrigierte Spracheingabe wird weiterhin über diverse Zwischenschritte in maschinenlesbare Sprache umgewandelt und an eine Testumgebung oder auch eine Schnittstelle zu einer entwickelnden Software, einem zu entwickelnden Produkt oder technischen System übermittelt, wobei die maschinenlesbare Sprache ausgeführt wird, um einen Testfall durchzuführen und, wobei das Ergebnis des Testfalls zurückgeführt und optional visualisiert wird. In one embodiment, generating a test case-specific algorithm from one or more test case schemas in a test generation section (333) includes extracting information about at least one function, one signal and one message from one or more test case schemas and inserting that information into a test case template, wherein the test case-specific algorithm includes a process flow in machine-readable language. In contrast to the prior art described above, the present invention analyzes, standardizes, and corrects various forms of natural language, such as mixed language, syntactically and according to other predefined rules. The corrected speech input is then converted into machine-readable language via various intermediate steps and transmitted to a test environment or an interface to software under development, a product under development, or a technical system. The machine-readable language is then executed to perform a test case, and the result of the test case is fed back and optionally visualized.

In einem Aspekt umfasst der erste Schritt (S1) des erfindungsgemäßen Verfahrens das Empfangen von einer oder mehrerer, zumindest einen Testfall definierender, textbasierter Anforderungen, umfassend zumindest anteilig natürliche Sprache, in einem Anforderungseingabeabschnitt (311). Textbasierte Anforderungen in natürlicher Sprache können sich erfindungsgemäße in einer Vielzahl von Eigenschaften unterscheiden, wie in der Sprache selbst, aber auch der Syntax, Grammatik, dem Wortschatz und der Rechtschreibung der gleichen Sprachen und sogar weiteren regionalspezifischen Einflüssen, wie Dialekten unterliegen, im Gegensatz zu konventionellen Anforderungsanalysen, wobei die Eingabe von Anforderungstexten bereits an bestimmte Bedingungen jener genannten Eigenschaften geknüpft ist, um die nachträgliche Verarbeitung der Eingabe, beispielsweise durch Tokenisierung, zu vereinfachen. Jedoch scheitern entsprechende Verfahren eben genau daran, die Eingaben in gewünschter Ausgestaltung zu erhalten. Im erfindungsgemäßen Verfahren werden daher keine Anforderungen an die Eingabe des Anforderungstextes gestellt, sodass jedermann eine Eingabe vornehmen kann, ohne beispielsweise an einer Eingabemaske zu scheitern oder unbefriedigende Ergebnisse zu erhalten. Die Eingabe in einer beliebigen Form natürlicher Sprache bringt den Vorteil, dass jedermann, auch unabhängig der Sprachkenntnis und mit geringen technischen Kenntnissen über das zu testende technische System Eingaben durchführen kann. In einer alternativen Ausführungsform erfolgt die Eingabe durch Einladen entsprechender Dateien, wie bereits im Beschreibungsabschnitt zum Dateneingabeabschnitt (310) genannt. In einer alternativen Ausführungsform erfolgt die Eingabe durch den Benutzer (120) der GUI innerhalb einer Eingabemaske. Durch die beiden Möglichkeiten, die Eingaben als Dateien einzuladen oder durch einen Benutzer (120) direkt einzugeben, kann der erste Schritt (S1) voll- oder halbautomatisiert ausgeführt werden. In einem Aspekt umfasst der zweite Schritt (S2) des erfindungsgemäßen Verfahrens das Generieren von jeweils wenigstens einem regulären Ausdruck für jede textbasierte Anforderung (350), in einem Anforderungsüberprüfungsabschnitt (312). In einer Ausführungsform umfasst das Generieren von regulären Ausdrücken, das Analysieren und Korrigieren der eingegebenen, textbasierten Anforderungen. In diesem zweiten Schritt (S2) werden die textbasierten Eingaben, in beliebiger Form natürlicher Sprache, analysiert und nach definierten Regeln umgestellt. Das Analysieren und Umstellen der textbasierten Eingaben erfolgt erfindungsgemäß mit technischen Mitteln des maschinellen Lernens, insbesondere mit Mitteln der Sprachverarbeitung natürlicher Sprache, sowie vorzugsweise durch ein erstes Sprachenverarbeitungsmodell oder LLM („large language model“). Das erste LLM kann jegliche bekannte Ausgestaltung annehmen, solange es eingerichtet ist, um natürliche Sprache zu analysieren und nach definierten Regeln umzustellen. Definierte Regeln können hierbei zum einen während des Trainings des ersten LLMs durch die entsprechenden Trainingsdaten vermittelt werden. Zum anderen können die definierten Regeln auch nachträglich kontrolliert oder verändert werden und durch eine Benutzerakzeptanzabfrage bestätigt oder verneint werden. Als Alternative zum speziell trainierten Sprachverarbeitungsmodell kann auch das Sprachverarbeitungsmodell aus einem Basissprachmodell bestehen, wobei die speziell für die Aufgabe der Erzeugung eines regulären Ausdrucks optimierte Ausgabe durch „Prompt Engineering“ erzeugt wird. Wie bereits beschrieben werden hierbei dem Basismodell Kontextinformationen übergeben, welche die Erzeugung von regulären Ausdrücken verbessern. Es lassen sich Beispiele für die gewünschten Ein-/Ausgaben als Teil des Prompts an das Sprachverarbeitungsmodell (LLM) übergeben oder es könne weiterhin zum Überführen von Anforderungen in reguläre Ausdrücke verschiedene Prompts mit Teilaufgaben verwendet werden, die beispielsweise zunächst die Evaluation von Kriterien für die regulären Ausdrücke durch das Sprachverarbeitungsmodell LLM, dann die Generierung von Verbesserungsvorschlägen durch das LLM und dann die erneute Evaluation der Kriterien auf Basis der Verbesserung vornehmen. In one aspect, the first step (S1) of the method according to the invention comprises receiving one or more text-based requirements, at least one of which defines a test case and includes at least a portion of natural language, in a requirements input section (311). Text-based requirements in natural language can differ in a multitude of properties according to the invention, such as the language itself, but also the syntax, grammar, vocabulary, and spelling of the same languages, and even further region-specific influences, such as dialects. This contrasts with conventional requirements analyses, where the input of requirements texts is already linked to certain conditions of those aforementioned properties in order to simplify subsequent processing of the input, for example, by tokenization. However, corresponding methods fail precisely because they do not obtain the input in the desired form. Therefore, in the method according to the invention, no requirements are imposed on the input of the requirements text, so that anyone can enter data without, for example, encountering an input mask or receiving unsatisfactory results. Input in any form of natural language offers the advantage that anyone, regardless of language proficiency and with limited technical knowledge of the technical system under test, can enter data. In an alternative embodiment, input is achieved by loading corresponding files, as already mentioned in the description section for the data input section (310). In another alternative embodiment, input is entered by the user (120) of the GUI within an input mask. The two options of loading data as files or entering data directly by a user (120) allow the first step (S1) to be executed fully or semi-automatically. In one aspect, the second step (S2) of the method according to the invention comprises generating at least one regular expression for each text-based requirement (350) in a requirement verification section (312). In one embodiment, the generation of regular expressions includes analyzing and correcting the input text-based requirements. In this second step (S2), the text-based inputs, in any form of natural language, are analyzed and rearranged according to defined rules. According to the invention, the analysis and rearrangement of the text-based inputs is performed using machine learning methods, in particular natural language processing methods, and preferably by a first language processing model or LLM (large language model). The first LLM can have any known configuration, as long as it is set up to analyze natural language and rearrange it according to defined rules. Defined rules can be provided during the training of the first LLM by the corresponding training data. Alternatively, the defined rules can also be subsequently checked or modified and confirmed or rejected by a user acceptance query. As an alternative to a specially trained natural language model (LLM), the LLM can also consist of a base language model, with the output specifically optimized for generating a regular expression being created through prompt engineering. As previously described, contextual information is passed to the base model to improve the generation of regular expressions. Examples of the desired input/output can be passed to the LLM as part of the prompt, or different prompts with subtasks can be used to translate requirements into regular expressions. These subtasks might, for example, first evaluate the criteria for the regular expressions using the LLM, then generate improvement suggestions, and finally re-evaluate the criteria based on these improvements.
